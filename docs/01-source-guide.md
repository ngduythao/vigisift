# How to read this source

A guided tour of the code and the reasoning behind it. It takes about an afternoon.

VigiSift has two halves:

- **Devices**: devices fire telemetry over
  MQTT, the server receives, stores and pushes it in realtime to the browser; users send commands
  down to devices.
- **Camera alerts for operators watching many sites**: each site runs its own
  [Frigate](https://github.com/blakeblackshear/frigate) handling cameras, person
  detection, recording and VLM scene summaries; VigiSift gathers every site's alerts
  in one place. Why not write the camera part ourselves: see `02-open-source.md`.

**About 5,000 lines of Python, 3,700 lines of tests.** Deliberately small so you can read it all.
Dependencies only point inward: `domain` ← `ports` ← `features`, while `infra` implements
`ports`; `tests/test_architecture.py` blocks wrong-way imports.

## The best lesson: two layers covering each other

Preventing duplicate commands here has **two layers**:

1. Application: `SELECT ... WHERE idempotency_key = ?` then return the old record
2. Database: `idempotency_key TEXT NOT NULL UNIQUE`

Tried breaking them and recorded the results:

| Removed | Test red? | Why |
|---|---|---|
| Only the application layer | **no** | INSERT hits UNIQUE → `IntegrityError` → reads the old record |
| Only the DB's `UNIQUE` | **no** | the application layer's `SELECT` catches it |
| **Both** | **red** | nothing is left to stop it, the device gets two commands |

This is why a good test pins a **guarantee**, not a **line of code**. And it's why
the question *"are two layers redundant?"* has an answer: no, each layer holds up
the other when it fails.

Ask yourself: `telemetry` from an unknown device also has two layers. Which?
(Hint: what `ingest.py` checks, and where `schema.sql` has `REFERENCES`.) Alerts from
an unknown site too: Mosquitto's ACL, then `UnknownSiteError` in `repository.py`.

## Results from Frigate (and from the VLM) must be validated too

Frigate is good software, but to VigiSift it's an **external system**, and the
summary in its payload is text **generated by a VLM**. `payload.py` checks before
storing: camera names and ids by regex, `severity` with only two values, suspicion level 0–2,
confidence 0–1, length limits on text. Unknown fields are ignored (a new Frigate field
doesn't break anything), but a field we use being wrong rejects the whole message.

Two details worth noting:

- **The log doesn't copy payload content**, only the names of bad fields
  (`test_a_malformed_review_is_logged_and_dropped` pins this). Model-generated text
  can be long, and can contain things that shouldn't be in logs.
- **A trap read from Frigate's source, not in the docs:** before sending a
  summary, Frigate widens `start_time`/`end_time` by up to 5 seconds at each end (to
  show the model more context), and saves the widened values too. So a summary message
  gives only **approximate** times; the `times_approximate` column records that.

## Merging independent of order

Frigate reports a review several times: `new` → `update` → `end` → `genai` (when the VLM
finishes summarising). Through MQTT shared subscriptions (instances sharing messages)
and the reconcile loop, reports can **arrive out of order or duplicated**. Rather than
trying to keep order, every merge is written so that **order doesn't matter**:

| Column | Merge rule |
|---|---|
| `severity` | once `alert`, stays `alert` |
| `objects`, `zones` | union of the two sets |
| `started_at` / `ended_at` | exact times beat approximate ones; of the same kind, the widest span |
| summary | travels whole, never mixing one's title with another's scene |

`test_every_arrival_order_ends_in_the_same_alert` runs **all 24 orders** of the four
messages and demands the same row. Tried breaking it: changing the "exact beats approximate" rule
turns this test **red** right away.

The test also caught a real fault while being written: three duplicates of **a new review** arriving
together made an operator see it three times. `SELECT ... FOR UPDATE` can't lock a row that
**doesn't exist yet**, so all three saw "not there" and all counted as new. Fixed with
`INSERT ... ON CONFLICT DO NOTHING RETURNING`: exactly one transaction wins the first
insert, and the rest wait at the unique index and then take the merge path.

In short: guaranteeing message order is costly and fragile at scale, so merges are commutative
and idempotent, and a test runs all 24 permutations.

## One definition of an alert

An alert has two suspicion levels: Frigate's, and the one VigiSift's rule re-check gives. The
"effective level" operators see is the higher of the two. It was once written out in six places
(five queries and a fallback in the page), and an index meant for suspicious alerts still filtered
on Frigate's level alone, so no query used it.

Now Postgres computes it once, as a stored generated column (`camera_alerts.level`), and one view,
`alert_list`, defines the alert as operators see it: the alert, its site's address and the latest
verdict. The queue, history, metrics, label export and live events all read that view, and only
`features/alerts/repository.py` touches the table.

The test written for this change found an older bug: several instances starting together on an
empty database failed with a duplicate key, because `CREATE TABLE IF NOT EXISTS` isn't safe to
run concurrently. `apply_schema` now takes an advisory lock first. Without it, the test failed 3
runs out of 3.

## When MQTT misses, ask again

MQTT is the fast path, not the sure path: a VigiSift restart, a broker drop,
or a flaky link between site and center all lose messages. Every 5 minutes `reconcile.py`
asks each site's Frigate API for reviews since the previous mark **minus a 15-minute
overlap**, then passes them through **the same merge function above**: re-reading what's there
changes nothing, so a wide overlap does no harm.

- Several instances: a Valkey lock per site, so only one instance reconciles each cycle.
- One broken site doesn't block others, and keeps its old mark to re-read next cycle.
- Sign in to Frigate once and keep the token; on a 401 sign in again **exactly once**
  (Frigate limits sign-in rate). Errors never carry the password.

---

## One identity per site

Each site's Frigate signs in to Mosquitto with its own user and may write only under
`frigate/<site>/#`; VigiSift may only **read** `frigate/+/reviews`. So the site in a
topic is the real site: even a compromised site can't fake another site's
alerts. `test_a_site_cannot_speak_for_another_site` runs on a real broker;
loosening the ACL to `frigate/#` was tried and the test went **red**.

## Sign-in: the fault an independent review caught

The first version checked "how many failures" then the password, then recorded the failure. Three steps,
two `await`s between: 100 concurrent requests all read "0 failures" and all got to
try. Another review agent wrote a script proving it: 100 real attempts, 0 blocked.
On top of that argon2 (deliberately ~25 ms of CPU) ran directly on the event loop, so 100
sign-ins stalled every request and WebSocket for about 2.4 seconds.

Fix: **increment the counter BEFORE checking the password**, with one atomic command (INCR in
a Valkey transaction); over the ceiling is refused, and a success gives the attempt back. Argon2 runs
in a thread, at most 4 at once. `test_a_burst_of_parallel_guesses_gets_no_more_tries_than_the_limit`
fires 50 parallel requests and demands exactly 5 password checks.

Two more details worth noting:

- **Count per (IP, username) pair**, plus separate ceilings for names and IPs. Counting by
  name alone lets a stranger with 5 wrong entries lock out an on-duty operator; counting by
  IP alone locks a whole center behind a NAT because one person mistyped.
- **Sessions carry a "password generation" (epoch).** Resetting a password bumps the epoch, so a stolen
  cookie dies at once, with no waiting to expire. This is where server-side sessions beat JWTs.

## Camera rules: desired state, not "send once"

When an admin edits rules (a bakery warehouse differs from a watch store), VigiSift saves first, pushes to
Frigate after, and **doesn't trust that a push finishes the job**:

- Frigate off at save time: the rules wait (`applied_sha` differs from `sha`), and the rule sync
  (`features/rules/sync.py`, every 5 minutes, apart from alert reconcile) pushes again.
- Someone restores an old Frigate `config.yml`: each sync pass re-reads the RUNNING config,
  and on drift pushes again. Really run: restored the file, restarted Frigate,
  VigiSift logged "drifted from Frigate, pushing again" and Frigate returned to the right rules.
- An admin edits again while the old version is being pushed: mark "applied" only if `sha` is
  still the version just pushed.

The same idea as a Kubernetes controller: compare desired state with actual state,
repeating until they match.

## Try it

```bash
make up            # postgres + mosquitto + valkey
make check         # lint + typecheck + test
make run           # API at http://127.0.0.1:8000
```

For devices, open three windows:

```bash
uv run python scripts/simulate_device.py lamp-1     # fake device
curl -N http://127.0.0.1:8000/devices               # view states
curl -X POST http://127.0.0.1:8000/devices/lamp-1/commands \
  -H 'Idempotency-Key: try-1' -H 'Content-Type: application/json' \
  -d '{"action":"ON"}'                              # send a command
```

Send the same command again with the **same** `Idempotency-Key` → returns `duplicate: true`,
and the device does **not** get the command twice.

For cameras, the whole stack in Docker (Frigate image ~1.5 GB, model ~6.2 GB):

```bash
scripts/fetch_samples.sh          # sample store video, sha256 checked
ollama serve & ollama pull qwen3-vl:8b-instruct
make demo                         # http://127.0.0.1:8000, Frigate at http://127.0.0.1:8971
docker compose logs frigate | grep -i password   # Frigate's first admin password
curl http://127.0.0.1:8000/alerts
```

## Why not call the VLM for every frame

An order-of-magnitude estimate: 100,000 cameras × 100 events/day × ~2,000 tokens per image,
at 5 USD/1M input tokens:

```
10,000,000 calls/day
20 billion tokens/day
~100,000 USD/day  ≈  3 million USD/month
```

So it must be tiered, and Frigate tiers exactly that way: motion detection (very cheap)
→ only regions with motion run the object detection model → only **alerts** are
sent to the VLM, **once when the review ends**, with up to 20 frames. Running
the VLM on a machine at the site (Ollama) makes the token cost zero, leaving only electricity.

In short: detection runs at the edge, and the VLM is called only when something must be put into
words. Frigate is already tiered that way, so VigiSift can focus on what a multi-site monitoring
center needs.

## What's still missing

- No single sign-on (SSO) yet: operators use their own VigiSift accounts.
- **MQTT between site and center has no TLS** in the dev build; sites over the internet must
  enable Mosquitto's TLS listener and Frigate's `mqtt.tls_*`.
- No backpressure when telemetry overloads: a full queue drops messages for that
  slow client only, with no way to tell the client it's being dropped.
- AI summaries take about a minute per review on a laptop (Frigate cuts at 120 seconds), so one
  VLM machine serves only about one summary a minute.
- The eval uses staged clips, not real CCTV, and the "suspicious" rules are hand-written per camera.

## Old numbers: local VLM measurements before moving to Frigate

Measured on the old build (VigiSift calling a VLM on one image itself), kept as history because
the lesson still holds for any small local model.

Running `llava:7b` on the same image, 6 runs per configuration:

| Configuration | Valid | Time |
|---|---|---|
| **Vietnamese** prompt, no retry | **2/6** | failed runs take **60–68 seconds** |
| **English** prompt, no retry | **5/6** | 0.4 – 2.8 seconds |
| English prompt **+ 3 retries** | **6/6** | 0.4 – 2.4 seconds |

Three takeaways, all numbers rather than feelings:

**1. Changing language fixes both accuracy and latency.** The 7B model writes Vietnamese
very badly: its sentences are nonsense, and worse:
when stuck it **rambles for 60+ seconds** and still produces no JSON. Making it answer in English
raises the correct rate from 2/6 to 5/6 and drops the time under 3 seconds. This is the
**cheapest** fix: no model change, no extra RAM. (The suspicious rules sent
to Frigate are also in English for this reason.)

**2. Retry is required for small models, not a precaution.** Even in English
1/6 still has a wrong type (`should_alert` not a boolean). Adding up to 3 tries gives
6/6. A ceiling on tries stops a hard image dragging on forever.

**3. Validation is the only barrier when running locally.** Claude has
`output_config.format`: the server ensures the schema. Ollama at the time only had
`format: "json"`, with no schema constraint, so the application's validation layer was the only
thing between the model and the database.

In short: with a local model, the application's validation is the only layer, because no server
enforces the schema for you.
